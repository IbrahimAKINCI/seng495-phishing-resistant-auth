# Metrics and measurement definitions (Module C)

Status: **written on 3 November 2026 as catch-up for the Week 3 task, updated on 4 November 2026 after the specification arrived** ("define the metrics precisely: attack outcome, friction in steps and seconds, server processing time"). The Week 4 requirement specification that the team submitted is not in this repository, so this document is written from the project description, the supervisor's requirements review, and the code that Module B already wrote (`web/friction.js`, `app/friction/logs.py`). When the two disagree, the specification is aligned to the agreed text, not the other way round, and the difference is recorded in "Open decisions" below.

The three quantities the project reports for every authentication method are the **attack outcome**, the **user friction** and the **server processing time**. Every number in the final report is produced by a script from these definitions. Nothing is typed into a table by hand.

## 1. Flows and methods

A **flow** is one complete task a user does from the web client. A **run** is one execution of a flow.

| Flow | Methods measured | Client name (`Friction.start`) |
|---|---|---|
| Login | password, password+totp, passkey | `login` |
| Passkey enrolment | passkey | `passkey_enrol` |
| TOTP enrolment | password+totp | `totp_enrol` |
| Recovery start / complete | recovery | `recovery_start`, `recovery_complete` |

A flow starts at `flow_start` and ends at `flow_end` in the friction log. A run that ends in an error is recorded and counted separately; it is never silently dropped.

## 2. Attack outcome

Every attack test ends in exactly one outcome, reported with what the test did:

| Outcome | Meaning |
|---|---|
| `blocked` | the service rejected the attack, and the test shows the rejection (status code or state) |
| `succeeded` | the attack reached its goal (for example a session was obtained) |
| `not_applicable` | the attack does not apply to this method, stated with the reason |
| `error` | the test itself failed to run; this is never counted as `blocked` |

Each test states the **expected outcome before it is run** (taken from the threat model). The result then confirms or refutes the statement. A test that only shows a valid case being accepted proves nothing; every check has a negative test.

## 3. User friction

Friction is measured on the system, not by observing people (no human subjects).

- **Step.** One of:
  - a click on a button that submits or confirms: 1 step;
  - filling one input field: 1 step, counted when the field is left with a value;
  - one authenticator interaction outside the browser page (touching or confirming a passkey prompt): 1 step;
  - opening the one-time code app and reading the code: 1 step;
  - scanning a QR code: 1 step.

  A page load or redirect is **not** a step. Typing in a field is the field step plus keystrokes (below). Steps that happen outside the browser cannot be seen by the client, so the harness adds them (the rule is in `web/friction.js`). This definition is fixed before any measurement is taken.
- **Input count.** The number of key presses inside input fields during the run (`keystroke` events).
- **Elapsed time.** `t_ms` of `flow_end` minus `flow_start`, measured in the browser with `performance.now()`.

## 4. Server processing time

The time from the moment the authentication request reaches the service to the moment the response is complete, in milliseconds (`server_ms` in `server_timing.jsonl`). It does not include network time or browser time. Argon2id is deliberately slow, so the password path is expected to dominate; the single-request figure is separate from throughput under concurrent load (Semester II).

## 5. Runs and statistics

- **Runs per flow:** 20, the same number for every method (starting point suggested in the supervisor's review).
- **Reported per flow and method:** median and 95th percentile. The median is used because timing distributions are skewed. The 95th percentile uses the nearest-rank rule: with 20 runs it is the 19th smallest value.
- **Spread:** a 95% confidence interval of the median by bootstrap. The 20 values are resampled with replacement 10,000 times, the median of each resample is computed, and the interval is the 2.5th to 97.5th percentile of those medians. The random seed is fixed so a re-run gives the same interval. Without an interval, a difference of twenty milliseconds cannot be told from noise.
- **Comparison between methods:** two methods are reported as different only if their intervals do not overlap; otherwise the report says the difference is not resolved.

## 6. Interface with Module B

Module B only **records** events; Module C **computes** the measurements. The files are written by the service (`app/friction/logs.py`) into `results/` (not committed, regenerated by the scripts).

- `friction.jsonl`, one line per client event: `run_id`, `flow`, `method`, `event` (`flow_start`, `step`, `keystroke`, `error`, `flow_end`), `t_ms`, `detail`.
- `server_timing.jsonl`, one line per authentication request: `request_id`, `endpoint`, `method`, `status`, `server_ms`.

The harness passes `?run=<id>` to the client so its runs match the friction events. Known weakness: `/metrics/events` accepts writes from anyone (Issue #11), so a result is only valid when every `run_id` in it was started by the harness.

## 7. Validation of the measurement code

The statistics code is tested against cases whose correct answer is known independently of the code: for example the median of `[1, 2, 3, 4, 5]` is 3, the nearest-rank 95th percentile of the numbers 1 to 20 is 19, and the bootstrap interval of a constant sample is a single point. These tests are in `tests_c/` (`test_stats.py`, `test_logs.py`) and run in CI. Slow measurement campaigns are scripts, not tests, and stay out of CI because they take minutes and CI machines are too noisy for timings.

## 8. Decisions

The revised requirements specification arrived on 4 November 2026 and settles the points that were open in the first draft of this document:

1. **Step rule:** the specification's rule (Section 7.1) is the same as Section 3 above (button, filled field, QR scan, authenticator prompt, opening the TOTP app: 1 step each; page loads and waiting are not steps). Expected counts from the rule: password 3, password + TOTP 6, passkey 2.
2. **Warm-up:** one warm-up run per flow and method, not counted among the 20 measured runs (FR-C4, Section 7.2).
3. **Resamples:** 10,000 (Section 7.2). `harness/stats.py` uses 10,000 by default with a fixed seed.
4. **Numbering:** the mapping to FR-C numbers is in `docs/requirements_c.md`.
5. **Still open:** the warm-up run is dropped from the statistics but must still be saved in the result file, marked as warm-up, so it can be reported separately. The format of that mark is decided when the campaign script is written (Week 10).
